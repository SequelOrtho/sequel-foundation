# Sequel Design Conventions

The UX rules that make Project Hub and the Acquisition Hub feel like one product family. Every new Sequel application adopts these from day one. Rules marked **(code)** are enforced or embodied by a module in this repo; the rest are conventions to carry into the app.

## 1. Brand & theming

- **One app, one entity — chosen first** (code: `brand/entities.ts`, `brand/theme.css` "Entity brands", `brand/EntityLogo.tsx`; v0.17.0). The family has three operating entities — **Sequel Ortho** (`SEQ`), **Fox Valley Orthopedics** (`FVO`), **OrthoNebraska** (`ON`) — and every app serves exactly one. Which one is the **first question when a new app is started**, before naming it (template `CLAUDE.md` step 0 runs `scripts/set-entity.mjs`). The choice is one constant (`lib/entity.ts`) stamped server-side on `<html data-entity="…">`; `theme.css` re-pitches every brand token, the `blue-*` ramp, the focus ring and the typefaces from that attribute, so `bg-brand` / `text-brand-navy` / `Button` mean *that entity's* colors with zero per-app CSS. No attribute = Sequel Ortho, so pre-v0.17 apps are unchanged. Logos come from `<EntityLogo entity=… />` (color on light, the guide's reverse treatment in dark mode), the favicon is a byte copy of the entity's `brand/assets/<key>/icon.png`, exporters take `docxBrand(entity)` / `headerFill(entity)`, and decks default to the entity's template layouts. Status colors (RYG, success, warning, danger, deck maroon) are **family-wide** — a red means the same thing under every logo. Written names follow each guide exactly (`ENTITIES[k].writtenForms`: "OrthoNebraska" is one word; FVO uses "orthopedic", never "orthopaedic"). Full palettes, typography and logo rules: `brand/BRAND.md`.
- **One token mechanism** (code: `brand/tokens.css`, `brand/theme.css`). All color flows through CSS custom properties; Tailwind utilities reference tokens (`bg-brand`, `text-brand-navy`), never raw hexes. Tailwind's default `blue-*` ramp is remapped to the active entity's brand ramp (Sequel blues, FVO greens, ON blues — `--brand-ramp-*`) so third-party-ish code adopts the brand automatically.
- **Dark mode is an attribute, not a media query** (code: `theme/theme.ts`, `ThemeToggle`). The resolved theme is stamped on `<html data-theme>` by a pre-hydration script (no flash), a three-state Light / Dark / Browser toggle persists in localStorage, and Tailwind's `dark:` variant is re-keyed to the attribute. Per-app localStorage key (`pi.theme`, `hub.theme`, …) so apps don't fight; the auto mode is stored as `"system"` and **labeled "Browser"** (it reads `prefers-color-scheme`, which is the browser's setting).
- **Text-safe brand color, guide color kept** (code: `brand/theme.css` `--brand-primary` / `--brand-bright`, `brand/palette.ts` `brandBright`; v0.28.0; owner ruling 2026-10-21, Mike: "Approved", UX audit Q1). `--brand-primary` (`text-brand`, `bg-brand`, `border-brand`) must read at 4.5:1 as text on the light ground and carry a white label as a button fill. Sequel's guide blue `#009DDD` is 3.1:1 on white, so Sequel's `--brand-primary` is the darker `#006A9C` (hover `#005A85`), and the guide blue lives on as `--brand-bright` (`bg-brand-bright`, `brandColors().brandBright`) for the mark, chart series and decorative grounds that carry no text. FVO's and ON's primaries already pass, so their `--brand-bright` equals `--brand-primary`. `tests/button-contrast.test.ts` checks every entity × theme.
- **Solid buttons flip to dark ink in dark mode** (code: `ui/Button.tsx`; v0.28.0; UX audit FND-1). Dark mode lightens `--brand-primary`, `--brand-navy` and `--brand-danger` so they read as text on a dark ground, which leaves white labels on them at ~2:1. The `primary`, `secondary` and `danger` variants therefore carry `dark:text-zinc-900`, like `accent` always has. A hand-rolled solid button does the same, or uses `buttonClasses`.
- **Disabled buttons lose their colour, not just their opacity** (code: `ui/Button.tsx` `BUTTON_DISABLED_CLASS`, `BUTTON_BUSY_CLASS`; v0.30.0; hub walk-through 2026-10-21, approved by Mike: "1-yes, 2-fix all items"). `disabled:opacity-50` over a dark-mode solid fill — a light blue over a near-black card — gave a mid blue with dark ink, the look of an *enabled* dark-mode button (Scheduler Save Changes / Apply, Project Hub Configuration Delete). Every variant now shares one disabled state: a neutral zinc ground (zinc-100 light; zinc-900 dark — deliberately not the zinc-800 an outline or ghost button turns on hover, so a disabled button never looks like an enabled one under the pointer), a zinc-500 label (≥ 3:1 on both, so it stays legible), a zinc border where the variant has one, in dark mode a 1px zinc-700 outline over the border line (`-outline-offset-1`, no layout change) so a borderless solid button keeps a visible box on a zinc-900 card, the not-allowed cursor and no hover change. The rules are `disabled:not-aria-busy:…` (specificity 0,3,0), so they beat the variants' hover and dark-mode rules whatever the stylesheet order, and a `busy` button — disabled too — keeps its fill, dimmed to 80% with the progress cursor, so it reads as working rather than unavailable. A hand-rolled button appends `BUTTON_DISABLED_CLASS` (or uses `buttonClasses`), never `disabled:opacity-*` on a coloured fill. Enabled buttons are unchanged.
- **An in-flight control says busy, never disabled alone** (v0.30.0). A button whose request is on its way uses `Button busy` (with `busyLabel` when the label changes) or sets `aria-busy` itself beside `disabled`: busy keeps the variant's fill, dimmed, with the progress cursor, while `disabled` alone now turns it grey, the look of an action that can't be taken. Controls that are unavailable *because* something else is in flight (a Dismiss beside a running Undo) stay plain `disabled`. Foundation examples: `SessionWatch`'s Stay Signed In (`aria-busy={staying}`), `UndoStrip`'s Undo Delete and `SectionSaveBar` (`busy`).
- **The dark yellow problem**: dark mode gets its own lightened/desaturated status values (see `theme.css`), never the light palette on a dark ground. Don't invent per-app dark values.
- **The theme layer owns the page ground** (code: `theme.css`): `body` background/color come from `--background`/`--foreground` (in `@layer base`, so an app's own body utilities still win), and `color-scheme` tracks `data-theme` so native scrollbars, pickers, and form controls follow the theme. Apps do not need — and template apps should not add — body-level color classes. `color-scheme` is not enough for native `<select>` popups on Chrome/Edge (Windows), which paint the open list on a light ground while each `<option>` inherits the dark `--foreground` — white-on-white whenever the select is `dark:bg-transparent`; so `theme.css` also gives `option`/`optgroup` the `--brand-surface` ground under `[data-theme="dark"]` (unlayered, v0.15.1). Hubs must not carry their own copy of that rule.
- **Muted/helper text is a token, never a raw gray** (code: `ui/Field.tsx` hint, `ui/SaveState.tsx`): use `text-brand-muted` (light `#707372` SEQ / `#5B6964` FVO / `#63666A` ON, dark `#a1a1aa` — all AA on their grounds) for hints, captions, secondary labels, empty states, and char counts. A raw `text-zinc-500` with no `dark:` pair is the single most common dark-mode bug across the hubs.
- **Contrast rescue is a net, not a license** (code: `theme.css` "Dark-mode contrast rescue"): in dark mode, un-darkened mid-gray text and light-gray border utilities are remapped to legible values — but only on elements with no `dark:text-*` / `dark:border-*` of their own. It exists so a missed pair degrades to "slightly generic" instead of "invisible"; new code still uses tokens or real `dark:` pairs, and rescued grays should be retired in sweeps.
- **Typefaces follow the entity** (code: `theme.css` `--brand-font-body` / `--brand-font-heading`, `ENTITIES[k].fonts`). Sequel Ortho and OrthoNebraska: Montserrat everywhere in the UI (ON's Gotham is licensed; its guide names Montserrat as the web alternative). Fox Valley Orthopedics: **Montserrat for headings, Open Sans for body** — `h1`–`h6` and the `font-heading` utility take the heading face automatically, so FVO apps load Open Sans (`--font-open-sans`) next to Montserrat. Generated documents: Montserrat (SEQ), Montserrat headings + Open Sans body (FVO), Arial (ON — its guide reserves Arial/Georgia for internal communications and presentations, and forbids Montserrat in print). Decks keep the template master's Montserrat. Monospace is Geist Mono everywhere. Load all of them via `next/font/google` with `--font-montserrat` / `--font-open-sans` / `--font-geist-mono` variables.

## 2. Color semantics

- **The accent = hand-off.** The entity's accent — Sequel lime `#CAD400`, OrthoNebraska lime (PMS 584) `#D2D755`, Fox Valley yellow (PMS 128) `#F4D659` — is reserved for assign / hand-off / delegate actions (code: `Button` variant `accent`, token `--brand-accent`). Views and passive links stay arrow-less and non-accent. Accent buttons take dark ink (zinc-900), never navy — navy washes out on a bright accent, in both themes (dark ink on yellow is also FVO's approved pairing).
- **Icon + label, never color alone.** Every status indicator pairs a shape/icon with text: the ApprovedBadge check-circle + "Approved · date" (code: `ui/StatusBadges.tsx`), RYG dots next to status words, the dumbbell chart's hollow-start/filled-end dots. This is an accessibility floor, not a style choice.
- **RYG stoplight vocabulary** (code: tokens in `theme.css`). Green / Yellow / Red / None, with separate `-text` variants for colored text. Thresholds are computed by shared pure helpers (see §4), and the same tokens drive UI chips and deck dot-cells.
- **A stoplight is a glyph and a word** (code: `ui/RygStatus.tsx` — `RygStatus`, `RYG_LABEL`; v0.29.0, UX audit FND-20). Render RYG status with `RygStatus`: a distinct shape per level (● green, ▲ yellow, ■ red, ○ not reported) in the `-text` tone, plus the word ("On track" / "At risk" / "Off track" / "Not reported", or the hub's own via `label`). A coloured dot alone fails colour-blind readers and Windows High Contrast, and the yellow dot is under 2:1 on white.
- **Charts take their chrome from the theme** (code: `brand/chart-theme.ts` `chartTheme`, `ui/chart-theme-hook.ts` `useChartTheme`; v0.29.0, UX audit FND-19). Recharts' defaults are a white tooltip that inherits light text in dark mode (white on white) and `#666` axis ticks (about 3:1 on a dark card). Every chart spreads `useChartTheme()` into `<Tooltip {...t.tooltip}>`, `tick={t.axisTick}`, `axisLine`, `<CartesianGrid stroke={t.grid}>` and the legend style; series colours stay `useSeriesColors()`. A chart that carries numbers people act on also gets a heading with units and a text alternative (a data table in a disclosure).
- **Maroon (`#8C1D2D`) for critical rows in decks** — an emphasized table row must not reuse the navy header fill (the entity's dark: Sequel navy, FVO dark green, ON blue) or it reads as a second header.

## 3. Interaction & state

- **Explicit sign-off for commitment actions; auto-advance only trivial transitions.** Anything that implies acknowledgement, approval, or an auditable decision (completing a gate, approving a phase, adopting a baseline) is an explicit user action — the apps are the record a steering committee reads. Auto-advancing "you typed something → in progress" is fine and appreciated.
- **An arm-then-confirm step keeps keyboard focus** (code: `ui/useConfirmStep.ts`; v0.29.0, UX audit FND-21). When a button swaps itself for Confirm / Cancel (Approve, Reject, Delete Team), arming moves focus to Confirm, and Cancel or Escape puts it back on the button that armed it — otherwise focus falls to the top of the page and a keyboard user has to find their place again. Put `armRef` on the arming button and `confirmRef` on Confirm, destructured (`const { armed, arm, cancel, armRef, confirmRef } = useConfirmStep()`) — the React compiler lint refuses `step.armRef` read off the returned object during render.
- **Modal dialogs are the native `<dialog>`** (code: `ui/Dialog.tsx`; v0.29.0, UX audit FND-18). A picker or a pre-export check that sits over the page uses `Dialog`: `showModal()` gives the focus trap, Escape and an inert page for free; it is named by its title, described by its description, has a labelled ✕ ("Close"), closes on a backdrop click unless `closeOnBackdrop={false}`, and returns focus to whatever opened it. Never a hand-rolled `fixed inset-0` div — three hubs had one that kept Tab and Escape behind it.
- **Save-state chip idiom** (code: `ui/SaveState.tsx`): `Saving… → Unsaved changes → Saved · 2:14 PM`. Toasts confirm saves; error toasts linger longer than confirmations (code: `ui/toast/`).
- **Every mutation ends with confirmation + a next step — never silence.** After any user action that changes data, the user must see (a) that it worked and (b) where to go from there: a toast with a contextual action link (`toastSaved("PM assigned", { action: { label: "View project →", href } })`) — or, for a reversible action, an Undo toast (`toastUndo("3 alerts removed", restore)`: a callback action that runs in place and lingers 10s; `{ label, onClick }` is accepted anywhere `{ label, href }` is), an inline `SaveStateIndicator` on form surfaces, or a redirect that lands on the affected entity. `router.refresh()` alone is not feedback. Queue rows must never silently vanish on success — confirm the action and offer the entity or the next item (code: `ui/toast/` action links; the toast ttl stretches when a link is attached).
- **Saving keeps you in place** (code: `ui/SectionSave.tsx`). A successful save never navigates away from the form — the confirmation is the toast plus the SaveState chip, and the user decides when to leave (Cancel / the origin-aware back link). Redirect-on-save is reserved for CREATE flows, which land on the newly created entity. List-row inline actions refresh in place.
- **Save is disabled until something changed** (code: `ui/SectionSave.tsx` + `ui/form-dirty.ts`). Every Save button is dirty-aware — disabled with "No changes to save" on its title until the form actually differs from its loaded state (`useFormDirty` snapshots uncontrolled forms; `shallowDirty` compares controlled state). A Save that would PATCH nothing is noise and a false audit entry.
- **Long forms save per section** (code: `ui/SectionSaveBar`). A form tall enough to scroll carries a compact Save bar inside each section (fieldset) so committing never requires scrolling to the bottom; the bottom Save-all remains for the full sweep. Both are dirty-aware, both confirm in place.
- **Navigation shows pending state too** (code: `ui/NavProgress`, `ui/LinkPendingHint`). A route transition that blocks on server work is an action like any other — it gets feedback within ~1s (NN/g response-time limits). Three layers, outermost first: `<NavProgress/>` mounted once in the root layout paints a brand-blue top bar on every internal link click and back/forward (fetch-then-push flows call `startNavProgress()` next to the fetch); slow segments ship a `loading.tsx` skeleton so the destination answers immediately; high-traffic tiles add an inline `LinkPendingHint` ("Opening…") on the control the user clicked. Every indicator holds invisible for its first ~250ms so fast hops never flicker.
- **Back to top on long scroll surfaces** (code: `ui/BackToTop`). Any page that regularly runs past ~4 screens mounts the floating pill; it appears only past ~2.5 viewports of scroll *and* on upward scroll intent (NN/g back-to-top guidelines), so short pages and downward reading never see it. Quiet outline styling — never the accent — icon + label, `data-no-print`. Pair with a sticky section jump-nav when the page has named sections; back-to-top gets you *up*, the jump-nav gets you *around*.
- **Locked areas render as non-links** — `role="link" aria-disabled` with the reason printed on the tile ("Complete due diligence to unlock"), never a dead `<a href>` and never a hidden tile (GOV.UK "cannot start yet" + NN/g). A locked *workflow step* (a phase not yet unlocked) may redirect to where the work continues; a URL the viewer's *role* cannot open answers with the no-access page instead (§4 "No access, not found, and errors") — never a silent bounce to Home. The PATCH/API layer enforces the same rule. **Keep all enforcement layers in agreement** — UI affordance, server gate, API validation.
- **Progressive disclosure for long lists** (code: `ui/ShowMore.tsx`): "Show N more / Show all (X) / Show fewer" with a live "Showing X of Y" count. No unbounded lists, no silent truncation.
- **Dropdowns over 12 items are fuzzy-searchable** (code: `ui/AdaptiveSelect.tsx`, `ui/SearchCombobox.tsx`, `ui/combo-match.ts`). A native `<select>` is fine up to 12 choices; past that it becomes a scroll-and-squint problem, so the field renders as the `SearchCombobox` — type-to-filter with fuzzy, ranked matching (prefix › word-prefix › substring › in-order subsequence › one typo/transposition), keyboard navigation, live result count, capped render with a "keep typing" hint. Render every dropdown whose list can grow (people, projects, entities, vendors, sites, taxonomies) as `<AdaptiveSelect>`: it counts the options and picks native vs. searchable at render time, so a picker that is small in one tenant and large in another obeys the rule in both without a code change; it takes `name` for form posts and `defaultValue` for uncontrolled forms exactly like a native select, and `labelClassName` when the host form has its own label typography (never re-style the control itself). Hard-coded enums (status, priority, role, month) stay native. `SEARCHABLE_SELECT_THRESHOLD` / `isSearchableSize` are the one definition of "more than 12" — never re-encode the number at a call site. (Owner ruling 2026-09-03, applied fleet-wide.)
- **List filters take several values** (code: `ui/MultiSelectFilter.tsx`, `ui/multi-select.ts` — `passesMulti`, `toggleMulti`, `multiSummary`). (Project Hub, 2027 plan list, PMO 2026-10-14: "all the Sprint and MGP projects that are priority 1 & 2.") A filter bar above a list or table is a question people ask with "or" inside one field and "and" across fields, so every list filter whose values are a set (entity, type, priority, sponsor, department, status, decision) is a `<MultiSelectFilter>`: values ticked in one filter combine as OR, separate filters combine as AND (chain `passesMulti(selected, row.value)` per filter), and a filter with nothing ticked is off — never a hidden "All" value that has to be unticked. Closed, it reads like the native select it replaces: the "All …" label when nothing is ticked, the option's label for one, both labels for two, a count beyond ("3 types"), with the full list in the tooltip. Open, it is a checkbox list with **Clear** and **Done**; Escape or a click outside closes it and returns focus to the button. Past the searchable threshold (`isSearchableSize`) the panel gains a type-to-filter box using the same fuzzy matcher as `SearchCombobox`. Show option labels the way the list's own column shows them, so the filter and the cell never disagree (a `KLO · Sprint` row is its own choice, not folded into Sprint). Single-value controls stay single: form fields, sort order, a ranking lens, and on/off flags ("Needs Analytics" is a checkbox). Where the selections are kept is the next rule.
- **List filters are remembered** (code: `ui/useRememberedState.ts`, `ui/remembered-view.ts`; v0.32.0). (Owner report, Project Hub 2027 plan list, 2026-10-22: "when making filtering selections and then opening an item and then clicking the link to go back to the 2027 list, it doesn't save the filters so the EPMO has to reset the filters every time they go into a single item. Filters should always be saved when clicking into a single item.") Every control of a list's filter bar — search box, every filter, sort, group-by, on/off flags, a ranking lens — is `useRememberedState("<list>.<control>", initial)` in place of `useState`: the value is kept in this browser tab's `sessionStorage` under one prefix, so a "← Back to …" link (a fresh render of the list), the browser's Back and a reload all show the list as it was left, while a new tab starts clean. Sign Out and the signed-out screen call `clearRememberedViews()`, and the hub's sign-in page mounts `ForgetSignedInState` (from `@sequel/foundation/session`) in its signed-out branch, so a session that ended on the idle timeout without either clears them too (owner ruling 2026-10-22, Mike: "yes" to "Should an idle sign-out that lands on the sign-in page also clear filters?"); the next person on a shared computer never inherits a list. Key by list and control, and put whatever changes the row set into the key (`plan-2027.entity`, not `plan.entity`), so one list's choices never filter another's rows. A stored value is read through `readLike` (it must have the initial value's shape, else the initial value wins); pass a module-level `read` when only some strings are valid (a sort-key union). The bar carries a **Clear Filters** button whenever anything differs from the defaults — remembered filters that can't be dropped in one click become a trap. Remembering is for view state only: never a form draft (that is the save-surface kit's job), and never the URL's job unless the page already carries its filters in the URL, in which case the back link carries the query.
- **Popovers stay on screen** (code: `ui/useFitInViewport.ts`, `ui/viewport-fit.ts`; v0.22.0). Every panel that opens from a control — top-nav section menus, notification/alert bells, account menus, filter and combobox popovers — keeps its whole width and height inside the window at every width. Anchor it to its button as usual (`absolute right-0` for header menus that open leftward, `left-0` for fields) and put `useFitInViewport(open)`'s ref on the panel: before paint it caps the width at the window less an 8px gutter, slides the panel sideways just enough to clear either edge, and caps the height at the room below it with an inner scroll; it re-fits on resize. `MultiSelectFilter` and `SearchCombobox` carry it already. (Owner report, Project Hub, 2026-10-14: signed in, the header carries the account control, the nav wraps to its own line, and the leftmost menu — "My Work" on User Roles — opened off the left of the screen, clipped and hard to read. The same right-anchored menu existed in the Acquisition Hub nav, the Scheduler Hub phone menu and the Missed Punch Hub alerts bell.) Check a new popover at 390, 768 and 1280px wide with the header in its signed-in state, opening the leftmost and rightmost control.
- **Field label geometry is the hubs' native idiom** (code: `ui/Field.tsx`, `ui/AdaptiveSelect.tsx`, `ui/SearchCombobox.tsx`): a block wrapper, an INLINE label span (it sits in the container's inherited line box exactly like every hand-rolled `<label class="block"><span>…</span>` field), the control carrying `mt-0.5`, hint and error `mt-1`. Never a flex-column label with its own gap: a `text-xs` flex item is a 16px line box beside ~21px inherited line boxes, so controls in the same grid row land ~5px apart (Project Hub, Onboard a Resource, 2026-09-10). Grouped controls keep the shape — `<fieldset><legend class="block"><span class={labelCls}>…</span></legend><div class="mt-0.5">…` — so a checkbox box aligns with the inputs beside it.
- **Row actions keep their places whatever the row's state.** (Project Hub, Projects Cleanup, 2026-10-09.) When a table or list row carries a group of actions whose labels or presence change with the row's state ("Archive" / "Restore", "Deprioritize" / "Re-prioritize", "Add evidence" / "Evidence ✎", a "Link KI" that only active rows show, a status chip that comes and goes), every action sits in a fixed slot so the same action lands in the same column on every row. In a right-aligned or flex group a wider label pushes every action before it, and a missing one shifts the rest, so rows stop lining up and the eye has to hunt. Give each slot a fixed width sized to its longest label (`w-20 text-left whitespace-nowrap`), or lay the group out as a CSS grid with fixed column tracks (`grid grid-cols-[2.25rem_3.5rem_5rem]`, each control `justify-self-start whitespace-nowrap`). When an action is absent for a row, render an empty `<span aria-hidden="true" />` in its slot instead of dropping it. A free-text box that shares the row with chips that come and go takes a fixed width (`w-64 max-w-full`), not `flex-1`, and a trailing control (the ✕ remove) pins right with `ml-auto`. Check every state together: render one row in each state side by side and confirm the columns line up. Live examples: Project Hub `app/admin/projects/ProjectsCleanup.tsx`, Audit Hub `components/ChecklistItems.tsx`, Acquisition Hub `app/pipeline/PipelineBoard.tsx` (`DealRow`).
- **Tags in table cells never break mid-label, and cell content never spills into the next column.** (Project Hub, Project Inventory, 2026-10-19: a "No PM" chip split into "NO" / "PM", "Pending Prioritization" wrapped across two lines, and a long VCP read ran over the Priority and Score columns.) A status tag or badge in a cell ("No PM", "Pending Prioritization", "Archived", "Back from 2026") is `inline-block whitespace-nowrap`, so it never breaks inside itself. The tags sit on their own row UNDER the cell's primary text (`mt-1 flex flex-wrap gap-1`), never inline after it with `ml-2`: the name keeps its own line, and several tags wrap as whole tags. The primary-text column takes a minimum width (`min-w-56` / `min-w-64`) so the table scrolls sideways instead of squeezing the name. Free text in a capped box (`w-60`, `max-w-64`) inside a `whitespace-nowrap` cell must reset `whitespace-normal break-words` on the box itself: a nowrap cell lets the text neither wrap nor widen the column, so it paints over its neighbours. Short fixed values (dates, numbers, IDs, names) stay `whitespace-nowrap`. Check a row with zero, one and several tags and the longest real text side by side. This follows the common design-system guidance (Elastic EUI table layout, IBM Carbon overflow content): no-wrap for short known-length values, wrap or truncate-with-tooltip for free text, horizontal scroll over illegible columns. Live example: Project Hub `components/TableTag.tsx` (`TableTag`, `TableTagRow`) in `app/projects/ProjectsTable.tsx` and `ProposalsTable.tsx`.
- **A scrolling wrapper is positioned** (code: `testing/scrollers.mjs` — `findUnpositionedScrollers`; v0.30.0). A wide table sits in an `overflow-x-auto` box so it scrolls inside itself on a phone. Text visible only to screen readers (`sr-only`, a column header's "Actions", a row's "Edit <name>") is `position: absolute`, and an absolute box is laid out against its nearest *positioned* ancestor, not its nearest scrolling one; when the scrolling box isn't positioned, that text escapes it and widens the page, so the whole page scrolls sideways at 390px (hub walk-through 2026-10-21: Scheduler schedules, Incident compliance, Audit data intake). Every scrolling wrapper — `overflow-x-auto`, `overflow-auto`, `overflow-x-scroll`, `overflow-scroll`, and a vertical `overflow-y-auto` list that holds sr-only text — carries `relative` (`relative overflow-x-auto`), or another position class it already needs (`sticky`, `absolute`). Hubs pin it from their unit suite: `const files = collectSourceFiles(process.cwd(), ["app", "components"]); const hits = findUnpositionedScrollers(files, { vertical: true }); expect(hits, formatUnpositionedScrollers(hits)).toEqual([]);` (import from `@sequel/foundation/testing/scrollers`); `vertical: true` checks the vertical `overflow-y-auto` lists the rule names as well as the horizontal scrollers; a scroller known to hold nothing absolute goes in its `allow` map (`"path"` or `"path:line"`) with a written reason. The check reads class strings in source (a `className={…}` expression counts whole, so a conditional `relative` passes); it does not see classes built at run time, so check a new table at 390px too: the page's `scrollWidth` equals the viewport.
- **Text inputs share the pickers' ground** (code: `ui/input-class.ts` — `INPUT_CLASS`, `inputClasses`; the same string is `AdaptiveSelect`'s native select and `SearchCombobox`'s input). Every hand-rolled `<input>` / `<textarea>` uses `INPUT_CLASS` (or `inputClasses("max-w-xs …")` for additive extras — width, rows, alignment, state variants, never a competing padding/border/background; prefer `max-w-*` for a width cap, and a plain `w-*` extra makes `inputClasses` drop the base `w-full`, since Tailwind v4 emits `.w-full` after `.w-32` and the extra would otherwise silently lose), so it renders exactly the pickers' box: `bg-white` in light mode, transparent over the dark card. An input with no background shows whatever it sits on, so on a tinted card (`bg-brand-surface`, `bg-*-50`) or a tinted page ground a prefilled required field reads as *disabled* next to the white pickers (Project Hub, Onboard a Resource, 2026-09-29). A hub's file-local `inputCls`/`fieldCls` constant should be `INPUT_CLASS` (or built from it), not a second copy. The box includes the invalid state (`aria-invalid` → danger border, with a `dark:aria-invalid:` twin because Tailwind v4 emits `dark:border-*` after a plain `aria-invalid:` border), so a control that sets `aria-invalid` per the required-fields rule needs no extra class. The box draws the family focus ring (`focus-visible:ring-2 ring-brand/50`) in place of the browser outline — keep it on every hand-rolled input (v0.28.0; owner ruling 2026-10-21, Mike: "1-yes" to keeping the 2px ring). Standalone native `<select>`s take the same box (`INPUT_CLASS`, or `inputClasses("w-auto")` inline). Dense table-cell editors and `text-xs` row selects that genuinely need a smaller box may keep their own class, but it still carries `bg-white dark:bg-transparent`. Without tailwind-merge, override a base token by replacing it in the string (e.g. swap `border-zinc-*` for a danger border), never by appending.
- **File pickers look like a button** (code: `ui/file-input-class.ts` — `FILE_INPUT_CLASS`, `fileInputClasses`; v0.30.0). A bare `<input type="file">` renders "Choose File  No file chosen" as plain text, so it doesn't read as a control (hub walk-through 2026-10-21: Scheduler import, Incident attachments, Audit data intake). Every file input takes `FILE_INPUT_CLASS` (or `fileInputClasses("mt-0.5")` for additive extras; as with `inputClasses`, a plain `w-*` extra drops the base `w-full`, and a plain `max-w-*` cap drops the base `max-w-full`): the native input stays — its label, keyboard behaviour, `accept`, `multiple` and form posting are the browser's — and its `::file-selector-button` (Tailwind v4 `file:`) is drawn as the `outline` Button: neutral border, white ground (zinc-900 in dark mode), rounded, padded, 32px tall, with the outline hover and none while disabled. The chosen file's name sits beside it in muted `text-sm`; keyboard focus draws the family ring on the input. The input is `w-full min-w-0`, so in a row with its Upload button (`flex flex-wrap items-end gap-2`, the input's wrapper `min-w-0 flex-1 basis-56`) a long name is cut short by the browser instead of pushing the row — and the page — sideways on a phone (Incident privacy Attachments, 2026-10-21). The `basis-56` (14rem) matters when the row holds another field too: `flex-1` alone sets a zero basis, so a wrapping row never wraps the picker and squeezes it to a sliver beside its neighbour (36px at 390 beside a 16rem select, Scheduler import and Audit data intake, 2026-10-22); with a 14rem basis it takes a line of its own on a phone. A hub that hides the native input behind its own picker buttons ("Choose Files", "Choose a Folder") uses `Button` / `buttonClasses({ variant: "outline" })` for them, keeps each label on one line (`whitespace-nowrap`) and lets the buttons wrap as whole buttons (`flex flex-wrap gap-2`), never inside themselves (Document Hub Upload at 390px). Check it at 390px with a long file name, in both themes.
- **Required fields: asterisk + legend, announced, validated on Save** (code: `ui/Field.tsx` — `Field required`, `RequiredMark`, `RequiredLegend`, `FieldError`, `fieldErrorId`; `ui/required-fields.ts` — `checkRequired`, `requiredSummary`; `AdaptiveSelect` / `SearchCombobox` take `required` + `error`). Owner ruling 2026-09-09, applied fleet-wide. Every required control is designated three ways, and every hub does it the same way: (1) the label ends in a danger-token asterisk (`<RequiredMark/>`, `aria-hidden` — decorative, never the only signal); (2) the control itself carries `required` / `aria-required="true"` so assistive tech announces it; (3) the form opens with `<RequiredLegend/>` ("* Required field", or "All fields are required" when nothing is optional) directly under its heading, so the asterisk is explained once per form (NN/g, "Marking Required Fields in Forms"; WCAG 3.3.2 Labels or Instructions). Optional fields stay unmarked; a long form where most fields are required may add "(optional)" to the few that aren't, never the reverse. Validation happens **on Save, not on keystroke**: the Save button stays enabled (dirty-gating and busy-gating still apply) and a click with a missing or malformed required field (a) renders a `<FieldError/>` under each offending control, linked by `aria-describedby` with `aria-invalid` on the control, (b) shows a danger Callout at the top of the form naming the fields (`requiredSummary`), and (c) moves focus to the first invalid field (WCAG 3.3.1 Error Identification, 3.3.3 Error Suggestion). Messages come from `checkRequired` so the words match across hubs — "First name is required", "Entity is required — choose one", "Enter a valid email address, like name@sequelortho.com", "Weekly hours must be at least 1". A form that instead disables Save until its required fields are filled (the older family idiom) is acceptable only because the marks + legend explain the disabled state — a disabled button with unmarked fields is the dead-end NN/g warns about — and it still surfaces the server's 422 inline; new forms and reworked forms use the Save-time check. Never rely on the browser's native validation bubbles (`noValidate` on forms that run this check). The server's zod schema re-validates the same rules and answers 422 — the client check is the explanation, the server check is the guarantee.
- **In-app alerts are a per-person inbox over a shared record — never the record itself.** (Established in the Missed Punch Hub, Sep 2026.) When a hub notifies people in-app (a header bell for approvers, a "new item routed to you" feed), the alert is one shared document addressed to its recipients, and every reader-side state — read, unread, removed — is a per-person receipt on it (`readBy`, `dismissedBy`: lower-cased identity keys), so one approver tidying their bell changes nothing for the others. Clearing an alert is cosmetic: it never deletes the alert, never touches the underlying request/record, and never writes the audit log — those have their own surfaces. The bell shows the newest few with the unread count and a "Manage Alerts" door to a full list; the list has **Unread** / **All** tabs (URLs, per §5), checkbox selection with *Select all shown*, bulk **Mark Read / Mark Unread / Remove** plus **Mark All Read**, and the same three per row. Opening an alert marks it read. **Remove is undoable** — the confirmation toast carries Undo (`toastUndo`), and an inline info strip keeps the same Undo on screen past the toast's lifetime and states that only the reader's own list changed. Bell and list subscribe to one client feed (`useSyncExternalStore` + polling) so the count and the list never disagree; the unread count is `aria-live`; unread rows carry a glyph *and* an sr-only "Unread:" prefix, never weight or color alone. The feed endpoint returns only what the client renders — not the other recipients' receipts or addresses. **The unread count also shows in the browser tab** (code: `ui/UnreadBadge.tsx`, `ui/tab-badge.ts`; v0.31.0; owner ruling Oct 22 2026, Mike: "1-yes, 2-yes" to the count in the tab title and on the tab's icon, "6-yes" to count only): mount `<UnreadBadge count={unread}/>` beside the bell, fed by the bell's own feed, and the tab reads "(3) Page · Hub" (exact to 99, then "99+") with a red count circle on the hub's icon (one digit, then "9+"). The title half is the accessible one — screen readers announce it on switching tabs; the icon half is never shown alone. **Count only**: no name, request or message text in the title or icon (tabs show on shared screens and screen shares). `SessionWatch`'s signed-out screen calls `clearUnreadBadge()` and the count stays off on that page for good; `SignOutForm` calls `clearUnreadBadge({ untilInput: true })`, so the count stays off while the sign-out leaves the page (a double-click or typing meanwhile never brings it back) and returns only at a click or keystroke away from the Sign Out form ten seconds or more later, which happens only when the sign-out was cancelled and the page stayed. Two ways the count comes back after Sign Out are accepted (owner ruling Oct 22 2026, Mike: "1-accept both"): a cancelled Sign Out (Stay on an unsaved-changes prompt), and a Sign Out still leaving after ten seconds when the person clicks elsewhere — in both they are still signed in and the tab matches the bell. A page that holds its own title (a `DocumentTitle` that puts back a title it didn't set) compares through `sameTitleIgnoringBadge` and puts back `stripShownBadge(previous)`, or it and the badge take turns rewriting the title; `stripShownBadge` takes a count off only a title the badge wrote, so a page whose own title starts "(12) " keeps it (owner ruling Oct 22 2026, "4-fix the two small items now"). Tests reset the badge through `@sequel/foundation/testing/unread-badge`, never the `ui` barrel — the reset would let a count back onto a signed-out tab. The installed-app taskbar badge (`navigator.setAppBadge`) needs an installable app and is not used (owner ruling Oct 22 2026: "3-lets hold off on this for now as what we get from 1 and 2 is good enough"). **Keep the count current in a background tab** (owner ruling Oct 22 2026, Mike: "4-agree with your recommendation"): the bell's poll keeps running while the tab is hidden, and still stops once nobody has clicked or typed in it for 10 minutes, so a tab left open picks up new alerts for those 10 minutes. Those checks count as activity, so they hold the idle sign-out off by at most 10 minutes, as in a visible tab (owner ruling Oct 22 2026, Mike: "2-yes and also fix the design rules").
- **Deletes can be undone for 30 minutes** (code: `undo/`, `@sequel/foundation/undo` + `…/undo/postgres`, `ui/UndoDelete.tsx` — `offerUndo`, `UndoStrip`, `postUndo`; v0.27.0; owner ruling Oct 20 2026, Mike: "For any hub that has a delete function … add an Undo Toast (timer 30 minutes) that allows Deletes to be undone. This would only be for pure delete actions that would remove data."; Scheduler Hub's Delete selected is the reference). **Which deletes:** a button that, once confirmed, erases a stored record someone entered — and whatever the database removes with it. **Not** access changes (removing a role mapping, an entity-access grant, a scope; revoking or deactivating a user — owner ruling Oct 20 2026, Mike chose "No, data deletes only" when asked "Should removing a role or access grant also get Undo?"), status changes that keep the row (cancel, retire, archive, dismiss, withdraw), replacements (re-upload a period, re-run a batch, replace-all import), housekeeping (expired rate windows, an aborted upload), or a row removed from a form that is not saved yet. **How:** the delete route records what it removes in the same transaction as the delete (Postgres hubs: `captureDelete` before the delete, the snapshot stored as json in the hub's `DeletedRecord` table; document stores: the document kept in a trash namespace) and answers `{ undo: UndoTicket }`; the surface calls `offerUndo(ticket, { onRestored })`, which fires the Undo toast (`toastUndo`, 10 s); when the toast goes, the `ToastViewport` every hub already mounts docks an `UndoStrip` ("… deleted. You can undo this until 3:42 PM" · Undo Delete · Dismiss) that keeps the same Undo on screen until the window closes, then hides itself. The offer lives in a module store like the toasts, so it survives the navigation most deletes end with (back to the list) — no hub mounts the strip by hand, and Undo runs once per ticket however many buttons are clicked. Undo POSTs the ticket to the hub's one restore route, `POST /api/undo`, which restores only when `undoRefusal` allows — the person who deleted it, once, within `UNDO_WINDOW_MINUTES` — and that person still holds the role the delete needed (a per-kind guard registry, re-checked at restore). The route marks the record restored in the restore's own transaction with a conditional write (`WHERE "restoredAt" IS NULL`), so two Undos at once can't both restore. The engine keeps every value exact (rows travel as `to_jsonb` text, never JavaScript numbers — bigint and numeric included), matches keys in the columns' own types, puts a self-referencing tree back parent first, and lets a column added since the delete take its default; it runs one statement per row, so on Prisma give the transaction room (`{ timeout: 15_000 }`). Every refusal but expiry reads the same ("This delete can't be undone."), so a ticket id never tells someone else whether a delete happened. A restore that would clash with what changed since (the same name re-created, a parent it belonged to deleted) rolls back whole and says `UNDO_CONFLICT_MESSAGE` — never a partial restore. Restore writes its own audit row; snapshots past the window are purged on the next delete, so a delete still erases the data after 30 minutes. Confirm dialogs say `UNDOABLE_DELETE_HINT` ("You can undo this for 30 minutes."), never "This cannot be undone." The strip holds the latest delete only; an earlier one stays undoable server-side until its window ends.
- **Ask the Hub is one family panel** (code: `assistant/AskHubPanel.tsx` — `@sequel/foundation/assistant/panel`; v0.33.0; rules in AI-CRAFT §2.6). A hub that offers the assistant renders `AskHubPanel` in its header: the header's one filled control, a brand pill with a sparkle whose label is screen-reader text below `lg` so the header keeps one row; a native modal `<dialog>` docked right (full width on a phone) that Escape, ✕ and a backdrop press close, with focus back on the button; starter questions in sentence case (they are questions, exempt from Title Case); Ask says busy (`busyLabel="Asking…"`); New Conversation clears the tab's copy; errors read in the route's own words, never a browser's or the AI service's. The hub passes its role, starters, the intro line (say what it never does, in the hub's words), the placeholder and the tooltip — never a second copy of the panel.
- **Working-ahead warnings, not locks, for soft dependencies** — an amber banner ("Phase 1 is not yet completed…") when a user works in a later phase, reserved locks for hard gates.

## 4. Architecture principles

- **Shared pure helpers when UI and an exporter compute the same thing.** If a filter/sort/score appears in a `.tsx` view and a deck/workbook exporter, extract it to a plain function that takes the domain object, and unit-test it. The preview and the download must call the same function — execs must read what the analyst just reviewed.
- **Domain knowledge lives in content/templates, generators assemble.** Editable-by-non-engineers content (KPI libraries, phase templates, question catalogs, model constants) stays in data modules; logic modules stay generic.
- **LLM model selection is configuration** (code: `llm/models.ts`). Call sites declare a task class (`prose` | `presentation`) and go through `modelFor` + `withModelFallback`; adopting a new model is an env-var change. Never hardcode a model id at a call site.
- **Cache-stable system prompts.** The large static framework prompt is the cache target (`cache_control: ephemeral`); all per-request data goes in the user message. Never interpolate timestamps/UUIDs/names into the system prompt.
- **Typed exceptions, never string-matching** (code: `llm/http.ts`). Map SDK error classes to `{status, error}`.
- **Deterministic gates bracket every model call** (code: `llm/input-gate.ts`, `llm/output.ts`). Input passes `gateLlmInput` before the request (size cap, control-char normalization, high-precision secret/PII redaction — with the user told what was redacted); output passes `parseLlmJson` + a caller-owned type guard before render — never a raw `JSON.parse` on model text. Contract failures surface as one typed error with a safe retryable message, never a blank panel. The full production framework — five boundaries, the 5-gate audit, per-infrastructure mapping — is [AI-CRAFT.md](./AI-CRAFT.md); read it before shipping any AI-backed feature.
- **Streaming beats platform timeouts — and narrates its stages** (code: `llm/stream.ts` + `stream-client.ts`). Any LLM-backed route streams SSE with heartbeats (`streamJob`), multi-step jobs emit status stages via `progress()` ("Querying…" → "Formatting…") that the UI surfaces through `consumeLlmStream`'s `onStatus` instead of a bare spinner, and the browser collapses the stream back to one awaited value. A hard timeout budget (`LLM_TIMEOUT_MS`) turns provider brownouts into the typed 504 + the route's deterministic fallback, never an indefinite spinner. Jobs that exceed the platform's streamed-function cap (~60s on Netlify; measure per platform) go to a background function returning **202 + poll**.
- **Registry-driven surfaces.** Exports, admin areas, and home tiles are data (a registry array), and the UI renders the registry. Adding a capability = appending a descriptor, not hand-editing three components.
- **Layout-rendered helpers fail soft on DB errors.** Anything the root layout renders on every page (header nav, scope/role resolution, session-to-person lookups) must catch database errors and degrade — empty list, null person, claim-derived role — never rethrow. A hard failure in the layout 500s *every* route, including public ones a DB outage must not take down (e.g. the Incident Hub's anonymous-reporting pages, Aug 2026). Page bodies may still fail on their own queries; the layout may not. Hide dependent chrome (selectors, badges) when the degraded value is empty rather than rendering hollow controls.

- **No access, not found, and errors** (code: `ui/AccessNotices.tsx`, `ui/access-copy.ts`; v0.26.0; owner request Oct 2026: "If a user in a Hub forwards a link … to a project / effort / section / item that the recipient user doesn't have access to given their role, please display a graceful error page … If they think they should have access, they should contact their system administrator for the particular hub"). A signed-in person who follows a forwarded or pasted link they can't use gets a branded page that says why and who to ask — never a silent redirect to Home, Next's bare "404 | This page could not be found.", or its "This page couldn't load" crash screen. Three cases, three boundary files at the app root, each rendering one foundation notice with the hub's full name (`appName`) and its own admin label (`adminLabel`, default "System Administrator"); contact wording is generic — no names (owner ruling): (1) **Role lacks the page or module** → the page gate calls `forbidden()` from `next/navigation` (needs `experimental.authInterrupts`) and `app/forbidden.tsx` renders `NoAccessNotice` (HTTP 403; `noAccessMessage`: "Your role in <Hub> (<Role>) doesn't include this page or the information on it. If you think you should have access, contact the <Hub> <System Administrator>."). Put it inside the hub's one page-gate helper (`requireSurface` and friends) so every call site converts at once; `forbidden.tsx` takes no props but may be an async server component that reads the viewer's role for `roleLabel`. Next renders the root `forbidden.tsx` into *every* page's RSC payload as the 403 boundary fallback, not only on a 403, so an async one runs its role lookup on every page load: wrap the hub's viewer resolver (the one the layout, the page gate and `forbidden.tsx` all call) in React `cache()` so one request resolves the viewer once (owner ruling 2026-10-19; measured 3 → 1 lookups per page in Incident, Missed Punch, Scheduler and Project Hub). `cache()` is per request and passes through outside a render, so route handlers are unaffected; pin it with a test that swaps in a memoizing `cache` and asserts one session / store read across several calls. (2) **A record that is missing, or whose existence is privileged** (peer review, a privacy case outside the viewer's lane, another person's request, a proposal the viewer doesn't sponsor, another entity's record) → `notFound()` and `app/not-found.tsx` renders `NotFoundNotice` (HTTP 404; `notFoundMessage`: "It may have been moved or removed, or it may not be open to your role in <Hub>. …") — one neutral sentence for missing and hidden alike, so the page is no oracle (owner ruling: the neutral page, not an explicit "no access", wherever existence is privileged). Never add a hint that implies the record exists elsewhere ("switch entity"), never render a case number or title. A module whose very existence is walled (peer review) gates on the role *before* any lookup, so a non-member gets the same answer for every id. (3) **An uncaught render error** → `app/error.tsx` and `app/global-error.tsx` are `"use client"` and render `PageErrorNotice` with the error `digest` and a retry that actually re-fetches: a bare `reset` only re-renders the boundary's children from the payload that already failed, so a transient server error comes straight back (Next 16 docs). In `error.tsx` pass `onRetry={() => startTransition(() => { router.refresh(); reset(); })}` (`useRouter` from `next/navigation`); `global-error.tsx` has no router, so pass `onRetry={() => window.location.reload()}`. `global-error.tsx` replaces the root layout, so it renders its own `<html>` (same `lang`, `data-entity` and theme stamp as the layout), `<head><title>{appName}</title></head>`, imports the app's `globals.css`, and applies the layout's `next/font` variables on `<body>` — keep the font definitions in a shared `app/fonts.ts` both files import, or the last-resort page falls back to the system face. The no-role 403 (`/auth/no-access`, below) and signed-out handling (§4 sign-out) are separate and unchanged; API routes keep their JSON 401/403/404. Workflow-step locks (§3 locked areas) may keep redirecting — this rule is about role. A record hidden by an own-data or class rule (a Therapist opening a colleague's checklist, a Patient Safety role opening an employee event) is case (2), not a redirect to the viewer's list: the link they followed should say it isn't available, not silently land somewhere else. **Verify the status on the `*.netlify.app` origin after deploy** (Netlify's runtime has dropped statuses before, see the no-role lesson), and expect a page under a `loading.tsx` to stream: the notice still renders, the status may read 200. Reference: Scheduler Hub `app/forbidden.tsx` / `app/not-found.tsx` / `app/error.tsx`; the template ships all four.
- **Sign-in is always on — no demo mode** (owner ruling Oct 20 2026, Mike: "Demo mode is no longer needed."). A hub has no `AUTH_MODE` switch and no branch that lets anyone in without signing in: the proxy sends every signed-out request to sign-in (pages) or answers 401 (`/api/*`), except the paths the hub deliberately makes public (the auth flow itself, token-gated lanes, anonymous intake). Signed out means no identity and no role — role resolvers grant nothing without a session, page gates call `forbidden()`, mutation guards answer 401; a hub's least-privilege default role is only for a signed-in person with no mapped role. The active-role cookie (the header Role selector) only chooses among the signed-in person's **granted** roles, never grants one. No self-selected demo role, no demo identity (a `DEV_USER_*` person, a "view as" or "I am" picker). **Local development signs in with Entra too** (Mike, Oct 20 2026: "That is fine.") — never add a dev-only sign-in or an identity fallback; tests mock the Entra session instead (`vi.mock("@/lib/auth")`). Each hub's CI deploy job proves the gate after the deploy with `scripts/smoke-sign-in-gate.sh` (the same script in Scheduler Hub, Incident & Event Hub, Project Hub, Audit Hub and Missed Punch Hub; only the probed paths differ): the site's `*.netlify.app` address comes from the Netlify API, never a hand-set variable, and a missing address fails the job, never skips the check; signed out, a staff page must be a redirect to `/auth/signin` on that origin or the hub's `AUTH_URL` custom domain, and a staff API must answer 401. Rollback guard: a build from before a hub's removal reads `AUTH_MODE` and treats a missing value as sign-in off, so keep `AUTH_MODE=entra` set on the Netlify site while such a build could still be redeployed, even though the current build reads nothing (Scheduler Hub, Incident & Event Hub, Project Hub, Audit Hub and Missed Punch Hub record this in their runbooks or CLAUDE.md). Fleet status (Oct 20 2026): removed in Missed Punch Hub, Audit Hub, Incident & Event Hub, Scheduler Hub and Project Hub; Market Expansion Hub still carries it (not yet scheduled); Document Hub has its own sign-in and never had demo mode; the app template has no sign-in wired yet and gets none of it when it does.
- **No role, no entry** (code: `access/`, `@sequel/foundation/access`; owner ruling Oct 13 2026). When Microsoft signs in someone the app has no role for, the `signIn` callback refuses them: it logs the attempt (`recordNoRoleAttempt` → the app's `AccessRequestStore`, plus a `[access]` console line with user, time, app) and redirects to `/auth/no-access` with a signed pass (`signNoRolePass`, keyed by `AUTH_SECRET`, 1 h). The page answers with **HTTP 403** by calling `forbidden()` (`experimental.authInterrupts`) and rendering `NoRoleNotice` from `app/auth/no-access/forbidden.tsx` — never a status set in `proxy.ts`, which Netlify drops (verified live, Oct 2026). `forbidden.tsx` takes no props, so the proxy forwards the query (`?t=&r=`) in a request header (`x-no-role-query`) for it to read; reference: scheduler-hub `app/auth/no-access/`. The notice carries the verbatim message `noRoleMessage(APP_NAME)`: "Your account doesn’t have a role in <hub's full name> yet. Contact the System Administrator to request access, then sign in again." Its **Request access** button POSTs the pass to `/auth/no-access/request`, which calls `requestAccess`: one email to **all** active System Administrators together (bootstrap-env admins included), at most once per person per 24 h, through the app's own Graph sender behind `NOTIFY_MODE` (off = logged, still queued). The admins' Users screen lists the queue (`pendingAccessRequests`). Rules: *what counts as a role is the app's call* — explicit role rows, Entra app-role claims, bootstrap admins, and any per-app link the app already admits people by (a provider record, a measure ownership) all count; only someone with none of these is refused. A role-lookup **error** is not "no role": fail closed to `?reason=unavailable` (the page renders the retry message itself, not `forbidden()`), never tell a legitimate user they lack a role. Sessions issued before the gate shipped carry no marker, so the `jwt` callback ends them once (`return null`) and everyone passes the gate on their next sign-in. Fleet status (Oct 2026): Scheduler Hub, Incident & Event Hub and Audit Hub enforce it; Project Hub and Missed Punch Hub are **exempt by owner ruling** (open intake: anyone in the tenant may submit); Market Expansion Hub has no roles yet (adopt when it grows them); Document Hub adopts it in the PR that moves it to Entra (the template's `sequel-hub-entra-wiring` skill carries it).

- **Signed out means no menu** (owner report Oct 14 2026). A visitor with no session sees only the brand link, the theme toggle and (where the app has one) a Sign in link — never the app menu, notification bell, role selector or account control. The header must decide this from the session *before* resolving a role: role resolution falls back to the least-privilege default role when nothing is granted, so a layout that asks for the role first renders that role's links (Project Hub showed "Intake" on its sign-in page this way). Pattern: check for a session at the top of the header nav (or around the layout's menu block) and return before any role or person lookup (`if (!session?.user) return null`). A hub that still carries an `AUTH_MODE` seam does the same through a pure `showAppChrome(mode, hasSession)` in `lib/auth/is-public.ts`, until its demo mode is removed. This covers every surface a signed-out visitor can reach: the sign-in and no-access pages, 404s, and any deliberately public pages (anonymous intake, share links) — those stay public, they just stop advertising staff links. Reference: Scheduler Hub and Incident & Event Hub `components/HeaderNav.tsx`.

- **Signing out and ended sessions — one flow, from any page** (code: `session/`, `@sequel/foundation/session`; Project Hub report, Oct 14 2026). Sign-out used to be an inline Server Action in the header form, which dead-ended in three ways: (1) a tab left open across a deploy held a stale action id, and the click failed with "Server Action … was not found on the server"; (2) after the idle timeout the proxy bounced the action POST to the sign-in page, where the action does not exist — same error screen; (3) the client-side redirect kept the router cache, so Back showed a signed-in page whose next click failed. The rules:
  - **Sign Out is `SignOutForm`**: a plain `<form method="post" action="/auth/sign-out">`, never a Server Action, so it works before hydration, across deploys and after the session is already gone.
  - **`/auth/sign-out` is `signOutRoute({ endSession })`** in `app/auth/sign-out/route.ts` (`endSession: () => signOut({ redirect: false })` on Auth.js). POST ends the session and answers **303 with a relative Location** to `/auth/signin?signedOut=1` (relative so the browser stays on its own host — behind Netlify the server can see the deploy permalink, where the person has no cookies), with `Cache-Control: no-store` and `Clear-Site-Data: "cache"` so Back cannot show a signed-in page. If the library throws, the session cookies are expired by hand and the person still lands signed out — sign-out never fails. A browser-flagged cross-site POST (`Sec-Fetch-Site: cross-site`) is refused without signing out. GET never signs anyone out (links, prefetches); it goes to the sign-in page.
  - **The proxy never touches the sign-out request** — on Auth.js, `export default bypassOnSignOut(auth((req) => { … }))` (a hub with its own outer `proxy()` wraps the `auth(…)` handler it calls). Auth.js's proxy wrapper re-issues the session cookie on every request it sees (that is the rolling idle timeout), so on `POST /auth/sign-out` the response carried two session cookies: the route's deletion and the proxy's refresh. `next start` emits the proxy's first and the deletion wins, so sign-out worked locally and in CI; Netlify's edge runtime appends the proxy's cookies *after* the function's, so the refresh won and nobody could sign out — the header's Sign Out landed on the sign-in page's "You're signed in · Continue / Sign Out", and that Sign Out failed the same way (every Auth.js hub, found on the Market Expansion Hub go-live, Oct 14 2026). A hub on its own session cookie whose proxy never writes cookies (Document Hub) needs nothing. Check it where it matters: a `POST /auth/sign-out` carrying a live session must answer with **no** `Set-Cookie` that gives the session cookie a value.
  - **The proxy answers a signed-out request in the shape its caller can use** — `signedOutResponse(req)`: a page — and any browser navigation, a download link under `/api/` included — gets a redirect to sign-in carrying `callbackUrl` back to the same page (Next's `_rsc` buster stripped; absolute on the request origin, because Next's proxy rejects a relative Location); a `fetch()` to `/api/*` gets **401 JSON** `{ error: "Your session has ended. Sign in again to continue." }` (a redirect there hands `fetch()` an HTML page — "Unexpected token '<'"); a Server Action gets Next's own `x-action-redirect` header, so the client does a full navigation to sign-in instead of throwing "An unexpected response was received from the server".
  - **The sign-in page sanitises `callbackUrl` with `safeCallbackUrl`** (same-origin paths only, never `/api/*` or `/auth/*`) and, when a session is still open (Back, a bookmark), renders `SignedInNotice` (who is signed in, Continue, Sign Out) instead of a second Microsoft round-trip.
  - **`SessionWatch` renders beside `SignOutForm`** (signed-in only): a sign-out in one tab broadcasts to the hub's other tabs (BroadcastChannel), and a tab that becomes visible re-checks the session at most once a minute; either way it shows a "You’ve been signed out" dialog whose **Sign In Again** returns to that page. When another tab or the server confirmed the end, it is the plain sign-in link; when the end is the expiry countdown's own estimate (below), it is the plain sign-out POST carrying the page as `callbackUrl` (`signOutRoute` passes it on, sanitised, to the signed-out sign-in page), so a cookie the estimate missed is cleared before the next person signs in — unless a tab has made a request since (the person signed in again elsewhere), when it is the sign-in link again and never ends that new session. Once the dialog shows, the tab sends no more session checks (each would re-issue the cookie). That dialog hides the page behind it (an opaque ground, not a dim), so on a shared computer the next person never reads the previous person's records (v0.29.0, UX audit review of v0.28.0; owner ruling 2026-10-21, Mike: "2-yes" to "Hide that page fully?"; the expiry warning still dims, since the person is still signed in). Both are native `<dialog>`s opened with `showModal()`, so they enter the browser's top layer above any `Dialog` left open — a z-index can't get above the top layer, and an overlay drawn that way left an open dialog readable on top of the signed-out screen with Sign In Again unclickable (PR review of v0.29.0) — and Escape never closes them. Event-driven only — never a poll, so an idle timeout still means idle.
  - **A warning comes before an idle sign-out** (code: `session/SessionWatch.tsx` `idleTimeoutSeconds`, `session/expiry.ts`; v0.29.0; owner ruling 2026-10-21, Mike: "add the warning", UX audit Q6; WCAG 2.2.6). Pass the hub's idle timeout (`idleTimeoutSeconds={sessionMaxAgeSeconds()}`) and SessionWatch shows "Your session is about to end" two minutes before it (`warnBeforeSeconds`), with **Stay Signed In**, which makes one session request (that request is what extends the rolling cookie) and closes; a 5xx, 429 or network failure keeps the warning up with **Try Again**, since a failed request may not have extended anything. Of the `/api/auth/*` routes only the session read counts as activity, and a failed request never does — a 4xx or 5xx reply or no reply at all (owner ruling 2026-10-21, Mike: "3-No"), so a page that polls after its session ended still reaches the signed-out screen. Two behaviours are kept by the same ruling ("1-OK, 2-OK"): coming back to a tab still reads the session, which extends it even while the warning shows, and the countdown end reads "You've been signed out" before Sign In Again clears a cookie that may live a few seconds more. The clock counts from the last request any tab of the hub made — page loads and same-origin fetches, seen through resource timing and shared between tabs in localStorage — never from mouse movement, and it never polls: asking `/api/auth/session` re-issues the cookie, so polling would keep an abandoned tab signed in forever. A click on a same-origin `<a download>` counts too (a download leaves no fetch entry), and each request is dated by its age, since `performance.now()` stops while the computer sleeps. A Stay Signed In still on its way when the countdown ends decides the outcome; it gives up after 10 seconds. When the countdown runs out the signed-out dialog shows without asking the server. The countdown is shown, not announced; the sentence is read once when the dialog opens.
  - **Microsoft sign-out is offered, not forced.** Ending the hub session leaves the browser signed in to Microsoft (a click on Sign in gets straight back in). Microsoft's own guidance is to also send the browser to the tenant's end-session endpoint (`entraSignOutUrl(issuer)`), but that signs the person out of Outlook and Teams on the web too, so the signed-out page offers it as "Shared computer? Also sign out of Microsoft" (`MicrosoftSignOutOffer`; owner decision Oct 14 2026: offered, never forced). Front-channel logout (Entra calling the app when the person signs out elsewhere) is not used: it runs in a cross-site iframe where `SameSite=Lax` session cookies are neither sent nor cleared.
  - Hubs on their own session cookie (Document Hub) use the same pieces: `signOutRoute({ endSession, sessionCookie })` with their cookie pattern and `SessionWatch` with their session check. Clear the cookie exactly once: if `endSession` already wrote the deletion through `cookies()` and then throws, Next merges it with the by-hand expiry into one `Set-Cookie` without `Max-Age=0` (emptied, not deleted — found on Document Hub), so catch secondary failures (an audit write) inside `endSession` and let only the clear itself throw.

## 5. Navigation & structure

- **The header logo links home — and says so** (code: `ui/HomeLink.tsx`). The logo + app title in the header are one `<Link href="/">` (with an accessible label) on every page — there is always a way back to the landing page without the browser back button. A bare `<div>` around the logo is a defect, not a style choice (surfaced by the Incident Hub tester review, Aug 2026). Clicking it confirms the departure with the family-standard "Bringing you back to Home…" info toast — §3's feedback rule applied to the one navigation whose destination is always nameable. Render the brand link as `<HomeLink>` (or call `toastHomeNav()` from a hand-rolled brand link's click handler); the toast fires only on clicks that actually navigate in this tab — never on modified/middle clicks (new tab) or re-clicks while already on Home.
- **Tiles carry an icon** (code: `ui/TileIcon.tsx`, `ui/AreaTile.tsx`; v0.20.0). Every hub tile — the Administration hub's area tiles first, and landing tiles wherever a hub has them — shows one small line glyph left of its title, so a grid of cards scans by shape before it is read. The glyphs come from the shared set (`TileIcon name=…`, `TILE_ICON_NAMES`): 24×24 grid, 1.75 stroke, round caps, no fill, `currentColor` in `text-brand-navy`, 20px beside the title, always `aria-hidden` because the title carries the meaning (icon + label, never the icon alone). Pick a glyph by what the area is *about* and reuse it for the same idea in every hub (`people-access` is "who can sign in" everywhere, `history` is an audit trail or decision log); a missing idea is a new glyph added here in the grammar above, never a one-off SVG or an emoji in an app. The icon lives on the registry descriptor (`icon: TileIconName`) so tile and menu read it from one place. Area hubs render `<AreaTileGrid>` + `<AreaTile href title description icon status attention emphasis>`: the whole card is the link, the footer carries the area's current state and — only when the area waits on the user — an attention line (⚠ + words). **Every navigational tile grid carries them, not just the Administration hub** (v0.25.0): landing tiles, section hubs (a module's own door page — Incident Hub `/safety`, Project Hub `/portfolio` and `/resource-management`), project-overview doors (Document Hub `/project/[id]`) and quick-action cards whose job is to take the user somewhere or hand them a file. KPI stat boxes, record cards (one card per project / team) and form panels are not tiles and take no glyph. Hubs keep their own card markup — the glyph goes left of the existing title in a `flex items-center gap-2` row; converting to `AreaTile` is optional. A **locked tile keeps its glyph**, muted (`TILE_ICON_MUTED_CLASS`), so a grid still scans by shape whatever the role, and says the lock in words on the card (the 🔒 marker and the reason sit on the reason line, never doubled up against the title). Inside one grid every glyph is distinct, enforced by the hub's registry test (`isTileIconName` + a uniqueness check) — the payroll package cards that share `banknote` are the one deliberate exception, being three cuts of one idea. Hubs without an area tile hub put the same glyphs on their admin section headings (Audit Hub `/admin`, Document Hub `/admin/users`) — the vocabulary is shared even where the layout is not. Reference: Incident & Event Hub `/admin` (where the pattern was established, Oct 2026), Scheduler Hub and Project Hub `/admin`, Missed Punch Hub and Market Expansion Hub landing / hub tiles, the template's `/admin`.
- **Tile ↔ menu parity.** Every hub tile appears in that section's nav dropdown, added in the same PR, both rendered from one shared registry — locked by a parity unit test so a hand-edited menu can't drift.
- **Breadcrumbs on nested routes** (code: `ui/Breadcrumbs.tsx`); the last crumb is the current page, unlinked, `aria-current`.
- **Origin-aware back-nav via a strict allow-list registry.** Deep links into an entity page carry `?from=<origin-key>`; the page resolves the key against a registry (`{ key → { label, href } }`) to render "← Back to {label}", and threads the key through edit round-trips (`returnHref`). Never echo the raw param into an href; guard lookups with `Object.hasOwn`; unknown keys fall back to the default back target. A subpage may consume a *single* origin key by strict equality when only one flow lands there — comment it as deliberately not generalized.
- **Tabs are URLs** (code: `ui/Tabs.tsx` + `ui/tabs.ts` — `Tabs`, `pickTab`, `tabHref`, `tabClasses`). Tabbed views drive the active tab from a query param through a strict allow-list (`?tab=`, `?view=`), rendered as `<Link scroll={false}>` with `aria-current="page"` — deep-linkable, in history, shareable. Links launched from inside a tab stamp the launching tab so returning lands where the user left. The default tab is the bare URL (omit the param when canonical). Resolve the param with `pickTab(raw, ALLOWED, fallback)` and render `<Tabs>` (per-tab `href` override when a link must carry more state, `query` to keep an origin `from` on every tab, `param` when the page already uses `view`). Keep the tab allow-list in a plain module, never exported from a `"use client"` file: a server page that imports it from a client module receives a client reference, not an array, and `allowed.includes(tab)` 500s on the first `?tab=` deep link (Missed Punch Hub, Sep 2026).
- **Queues act-and-advance.** A worklist (assignment queue, triage inbox, approval list) never strands the user after an action: the item's departure is confirmed (toast + link, per §3), a session-local record strip preserves what was just done, visited/handled rows are marked (icon + label), and the surface the queue hands off to offers a way back to the queue. Entity names rendered anywhere (tables, cards, panels) are links to their detail page — a plain-text name with a detail page is a dead-end micro-moment.
- **Names open the editor wherever an Edit affordance exists.** On any surface that carries an Edit link or button for a resource (a table row, a card, a panel header), the resource's *name* is a second door to that same editor — same href for a navigating Edit link, same toggle handler for an inline editor, gated on the same edit permission. For viewers without edit rights the name stays plain text (or keeps its detail link per the queues rule above). The Edit affordance itself remains — the name is an addition, never a replacement, and the two must never diverge in target (established portfolio-wide in Project Hub, Aug 2026).
- **No zero-exit pages.** Every page offers at least one contextual next step beyond the global nav. Empty states double as navigation: explain what belongs here and link the create/next action.
- **Print is a feature** (code: print block in `theme.css` + `ui/ExportBar.tsx`): every read-only view saves cleanly to PDF; chrome and export buttons carry `data-no-print`.
- **Every page starts with a skip link and has its own title** (code: `ui/SkipLink.tsx` — `SkipLink`, `MAIN_CONTENT_ID`, `titleTemplate`; v0.29.0, UX audit FND-15; WCAG 2.4.1, 2.4.2). The root layout renders `<SkipLink />` as the first thing in `<body>` (hidden until a keyboard user tabs to it) and the page content in `<main id={MAIN_CONTENT_ID} tabIndex={-1}>`. Its metadata title is `titleTemplate(APP_NAME)` — `{ default: APP_NAME, template: "%s · APP_NAME" }` — and every page exports a `metadata.title` (or `generateMetadata`) naming the page, so browser tabs, history and screen readers say "Master Schedule · Sequel Scheduler Hub", not the app name on every page. The 403 / 404 / error pages carry titles too (global-error renders its own `<title>`).
- **Header controls fit a phone** (code: `theme/ThemeToggle.tsx` `compact`; v0.29.0, UX audit FND-17). The ThemeToggle shows its icon alone below the `sm` breakpoint by default (`compact="phone"`), keeping the mode in its accessible name and tooltip; the header row wraps (`flex-wrap`), the signed-in email hides below `sm`, and Sign Out never wraps (`whitespace-nowrap`). Check every header at 390 px wide: nothing may push the page sideways.

## 5a. Navigation & flow review checklist

Run on every new/changed page and flow (synthesized from NN/g cognitive-walkthrough + menu/breadcrumb guidance, GOV.UK confirmation pages, Baymard back-button research, MeasuringU first-click). Score pass/fail; rate failures 0–4 (frequency × impact × persistence); fix 3s and 4s before merge.

Per page:
- **P1 Where am I?** — current section lit in the nav; title matches the link that got you here.
- **P2 Where can I go?** — global nav present; breadcrumb when ≥3 levels deep.
- **P3 First click is obvious** — a fresh colleague's first click for the page's #1 task is correct.
- **P4 No dead end** — ≥1 contextual next-step link beyond the global nav.
- **P5 Empty state navigates** — zero-data view explains + offers the create/next CTA.
- **P6 Back behaves** — back returns to the perceived previous view with state intact.

Per flow:
- **F1 Walkthrough** — at each step: right goal / control noticed / label connects / progress visible.
- **F2 Exit at every step** — cancel/back available, non-destructive; no trap states.
- **F3 Completion answers "what now?"** — confirmation + next-step link (§3 post-action rule).
- **F4 Queue actions advance** — next item or state-preserved return, never a dead stop.
- **F5 Path isn't lost-making** — the happy path is short and each hop is a confident choice; don't budget clicks, budget confusion per click.

## 6. Accessibility floor

- Visible brand focus ring on keyboard focus (`:focus-visible`, in `theme.css`), never removed. It sits in `@layer base`, so a component's own `focus-visible:ring-*` / `focus-visible:outline-none` wins over it, and it never changes the element's corner radius (v0.28.0, UX audit FND-12).
- **Windows High Contrast keeps every state** (code: `theme.css` "forced colors", `ui/Toast.tsx`, `ui/SearchCombobox.tsx`; v0.28.0, UX audit FND-13). Forced colors drop box shadows (Tailwind rings) and repaint fills, so a state shown only by a ring or a fill disappears. The theme puts a `Highlight` outline on focus, chosen options and pressed toggles and underlines the current tab and breadcrumb; components whose meaning rides on a fill add a `forced-colors:` border or outline of their own.
- **Toasts are announced from regions that are always there** (code: `ui/toast/ToastViewport.tsx`; v0.28.0, UX audit FND-6–8). The viewport renders one polite `role="status"` region and one assertive `role="alert"` region on every page, and toasts appear inside them; a live region that mounts together with its message is often not read. Danger toasts go to the assertive region, the rest to the polite one. A toast's timer pauses while the pointer is over it or focus is inside it and resumes with the time it had left (WCAG 2.2.1), and its Dismiss button is at least 24px square (WCAG 2.5.8).
- **Searchable dropdowns follow the arrow keys aloud** (code: `ui/SearchCombobox.tsx`; v0.28.0, UX audit FND-3–5). Focus stays in the input and `aria-activedescendant` names the active option, so screen readers read each option as the arrow keys move; the active row is a visible ring (not only a tint), the chosen option carries a ✓, and group headings label their options (`role="group"`).
- **A hint describes its control, never names it** (code: `ui/Field.tsx`, `fieldHintId`; v0.28.0, UX audit FND-10). The `<label>` holds the label text only; hint and error sit after it and are tied to the control with `aria-describedby`, so a screen reader reads "Password, edit text … First time here? Use your temporary passcode" instead of folding the hint into the name. `Field` wires a plain `<input>` / `<select>` / `<textarea>` child itself; a component child points its control at `fieldHintId(id)` / `fieldErrorId(id)`. A wrapper or component child with no `id` (Field can't reach its control) keeps hint and error inside the label, so they are still read out with the name (owner ruling 2026-10-21, Mike: "3-yes"); give the control an `id` to move them out.
- **Focus never falls off the page** (code: `ui/ShowMore.tsx`, `session/SessionWatch.tsx`; v0.28.0, UX audit FND-9 / FND-11). When the button that had focus disappears (Show All, Show Fewer), focus moves to the button that took its place. A modal dialog renders into `document.body` and makes the rest of the page `inert`, so neither Tab nor a screen reader's browse mode can wander behind it.

- Minimum tap-target heights on all buttons (code: `ui/Button.tsx` sizes).
- `aria-live` on dynamic counts; `role="alert"` on danger callouts, `role="status"` elsewhere (code: `ui/Callout.tsx`).
- WCAG ≥ 4.5:1 for text chips (the emerald badge pairing is pre-checked).
- **Motion honors `prefers-reduced-motion`** (code: motion tokens + reduced-motion overrides in `theme.css`). Animated affordances drop the animation but keep the feedback visible — the nav bar becomes a static translucent strip, fade-ins appear instantly, `BackToTop` scrolls without smoothing. Information never rides on motion alone.

## 7. Writing & labels

- **Title Case for buttons, tiles, and nav items** — every word of a multi-word label is capitalized ("Portfolio Hub", "Audit Log", never "Portfolio hub"), across the top-nav menus and menu entries of every hub; sentence case for body and hints. (Owner ruling 2026-09-01, after sentence-case labels crept into the Project Hub's Portfolio and Admin menus.) Short function words (a, an, and, as, at, by, for, from, in, of, on, or, the, to, with) stay lower case except as the first or last word ("Reset to Default", "Sign In"). Both halves of a hyphenated word are capitalized ("Revoke Sign-Off", "Go-Live", "Re-Run", "Pre-Expansion"; owner ruling 2026-10-21, Mike chose "Both halves (Sign-Off, Go-Live)"). The same rule covers links styled as buttons, arrow links ("Open Timeline →", "← Back to Projects"), toast actions and tile calls to action; each hub's `tests/button-title-case.test.ts` guards it, and a hub's user guide names each button exactly as it reads.
- **The arrow (→) means hand-off** — pair it with accent actions; plain views stay arrow-less.
- Say what unlocks a locked thing ("Complete due diligence to unlock"), not just that it's locked.
- Error messages name the likely cause and the fix ("the configured API key lacks permission for this model — check ANTHROPIC_API_KEY").

## 8. Verification habits

- **Verify every render state a change touches** — pre-gate and post-gate, with and without an active record, empty/error/loading — not just the state you developed in.
- **Every user-facing PR regenerates the app's guide** in the same PR (docs-kit convention): the guide is a committed artifact and drifts silently otherwise. Validate by extracting the docx text and checking new wording present, stale wording absent.
- Deck/exporter changes follow the render-verify workflow in [DECK-CRAFT.md](./DECK-CRAFT.md).
- **CI scans pages for accessibility and dead links** (code: `testing/a11y.mjs` + `a11y.d.mts`, plain JavaScript so Playwright can load it from node_modules — `@sequel/foundation/testing/a11y`; v0.29.0; owner ruling 2026-10-21, Mike: "Approved … 5-yes", UX audit Q5 / FND-22). Each app's CI runs a Playwright test over its key pages, signed in as a test user, in light AND dark (`themeInitFor`): `@axe-core/playwright` with `withTags([...A11Y_TAGS])` must report no serious or critical issue (`blockingViolations` — an exception needs a written reason in `allow`), and every same-origin link on those pages (`sameOriginLinks`) must answer below 400 (`findBrokenLinks` with a fetcher over the signed-in `page.request`). Off-site links are not fetched, so a vendor outage never fails a build. It is a floor — automated checks find a third to a half of problems; a keyboard pass is still part of review.
- **AI-behavior changes rerun the feature's golden set.** A prompt edit or model bump can fix one case and quietly break twenty-five others; "tried a few prompts and it looked fine" is not verification. Each AI feature keeps a golden set of realistic queries and runs it before shipping prompt/model changes — and passes the 5-gate audit in [AI-CRAFT.md](./AI-CRAFT.md) before its first beta.
