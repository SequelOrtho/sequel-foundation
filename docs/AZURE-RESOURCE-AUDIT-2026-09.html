How to read this

Every figure was derived from the code, schemas, seeds, deploy configuration, one real production build, and platform documentation. None of it comes from live telemetry, because this audit held no Netlify, Neon, or Anthropic console credentials. Each number carries a confidence tag; the last section lists the five console checks that turn estimates into measurements in about an hour.

Measured read from code, config, a real build, or a documented production count Derived computed from measured inputs (rows × bytes per row, page loads × payload) Assumed a stated planning assumption; the derived figure moves with it

The five answers at a glance

1
Number and stats of the web applications (CPU, memory)

5 deployed apps, all Next.js 16 on Netlify. Each runs as one serverless function at 1,024 MB RAM / ≈0.6 vCPU-equivalent, scale-to-zero, no reserved instances. Three apps also run a background or scheduled function. Two further repos (the shared foundation library and the app template) consume no runtime resources.

2
Number and size of the databases

4 Neon Postgres databases + 1 document store (Netlify Blobs; an Azure SQL adapter is written but not provisioned). Fleet total ≈0.1 GB today, ≈0.4–0.6 GB at 12 months, plus ≈0.5 GB of uploaded attachments at 12 months. No single database exceeds 0.25 GB within a year.

3
Size of the database server

Neon serverless, one project per hub. 1 Compute Unit = 1 vCPU + 4 GB RAM, autoscaling from 0.25 CU (0.25 vCPU / 1 GB), capped at 2 CU on the Free plan and up to 16 CU on paid plans, suspended after 5 idle minutes. At this fleet's load the computes sit at the 0.25 CU floor almost all the time.

4
Data between applications and databases at peak

≈0.2–0.35 GB per peak hour fleet-wide today (≈15–25 GB per month); ≈0.6–0.9 GB per hour at 12-month adoption, up to ≈2 GB per hour if two unbounded read paths are left as they are. Under 2 queries per second fleet-wide.

5
Data between applications and users at peak

≈0.3–0.45 GB per peak hour fleet-wide (≈1–1.2 GB per day, ≈25–35 GB per month). Pages are 50–300 KB each; the largest single transfers are 1–4 MB PowerPoint exports and hourly calendar-feed polling.

Bottom line for Azure sizing. This is a low-concurrency, small-data fleet. The binding constraints are memory for in-process Office-file generation and ingest (1 GB minimum, 2 GB comfortable), request timeouts for 60–120 second AI calls, a job runner for three long-running lanes, and connection pooling. CPU, storage, and bandwidth are not constraints at any tier.

Suggested Azure equivalents (recommendation, not a measurement)

  • Web tier. One App Service Linux plan P1v3 (2 vCPU / 8 GB) hosting all five apps as separate web apps, or P0v3 (1 vCPU / 4 GB) per app if isolation matters. Aggregate load is under one request per second. Memory headroom for Office-file generation drives the size, not CPU. Keep one always-on instance per app: every page is rendered on demand, so 1–3 s cold starts are user-visible.
  • Job tier. One Container Apps Job or Functions (Premium or Flex) runner for the three long lanes (Project Hub AI jobs, Acquisition Hub augment, Scheduler nightly horizon) and the two GitHub-cron tasks. All three lanes are already token-gated HTTP callbacks, so only the trigger moves.
  • Request timeout. At least 120 s on the web tier for AI routes, with streaming enabled and response buffering off.

Items the move should plan for

  1. Three long-running lanes need a runner. Project Hub AI jobs, Acquisition Hub augment, Scheduler Hub nightly horizon. Each is a token-gated HTTP callback today; only the trigger and duration cap change.
  2. Netlify Blobs has two consumers to replace. Incident & Event Hub attachments need a BAA-covered Azure Blob container (the spec already names this seam). Acquisition Hub documents move to Azure SQL, whose adapter exists but needs its one-time DDL run and tests.
  3. Connection pooling. One pg pool per instance today. Use Flexible Server's PgBouncer for web traffic and a direct connection for the two interactive-transaction lanes.
  4. Bound the four unbounded reads before user growth. Audit Hub charges and productivity, Scheduler dashboard, Project Hub projects list, Incident Hub audit admin page. These, not user count, decide whether app-to-database traffic stays under 1 GB an hour at 12 months.
  5. Audit-log retention. Three hubs append audit rows with no pruning; together they are the largest growth line in the database table above.
  6. Request timeouts and streaming. AI routes need at least 120 s. Acquisition Hub exports need streamed responses above 4.5 MB to work, which they do not on Netlify today.
  7. Auth go-live is a gate, not a migration task. All five apps run with auth off; the Audit Hub's only protection is a Cloudflare IP allow-list. Entra should be on before any Azure endpoint is public.
